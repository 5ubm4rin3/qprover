# QProver v2.5 Property-Directed Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the current global macro-free Track04 search with a property-directed, stateful, portfolio exploit synthesizer while preserving organizer-Harness proof semantics and the official CLI/output contract.

**Architecture:** Keep the existing compiler-backed analysis, generic QUBO/search core, Z3 parameter solver, minimizer, and organizer Harness verifier. Add compiler-backed invariant facts and a property/resource slice, narrow QUBO to short-horizon action ordering, separate skeleton planning from concrete parameter evaluation, then add a persistent SearchAttacker runtime and shared state frontier. Search-time invariant truth is the original compiled `Invariants.checkAll(target)`; only fresh organizer `Harness._prove` may produce exit `0`.

**Tech Stack:** Python 3.12/3.14-compatible code, Solidity 0.8.24, EVM Cancun, Foundry 1.7.1 submission image, NetworkX, Z3, existing QProver search core.

**Spec:** `docs/superpowers/specs/2026-09-17-qprover-v2.5-property-directed-search-design.md` and `docs/superpowers/specs/2026-09-17-qprover-v2.5-property-directed-search-self-review.md`

## Global Constraints

- Production Track04 search remains macro-free and target-name/known-witness independent.
- One concrete candidate execution followed by invariant checking equals one `--max-attempts` unit.
- Static property interpretation guides ranking only; it is never the runtime truth oracle.
- Search-time invariant truth uses the original compiled `Invariants.checkAll(target)` once the persistent runtime is introduced.
- Final exit `0` always requires fresh organizer Harness reproduction.
- Same source bytes, manifest, seed, and pinned toolchain must produce deterministic candidate ordering and final artifacts.
- No compile/infrastructure failure may be learned as a vulnerability/action revert.
- All new behavior follows TDD: failing regression first, verify RED, minimal implementation, verify GREEN, then refactor.
