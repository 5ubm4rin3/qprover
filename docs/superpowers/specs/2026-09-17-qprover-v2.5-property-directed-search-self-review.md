# QProver v2.5 Design Self-Review — Normative Clarifications

This file is a normative companion to
`2026-09-17-qprover-v2.5-property-directed-search-design.md`.
Where wording in the original design is ambiguous, the rules below take precedence.

## 1. Search-phase invariant truth

The fast search runtime MUST NOT reimplement organizer invariants in Python or in a second expression language.

`Invariants.sol` is compiled once with the target closure and deployed in the search runtime. After a concrete candidate or successful prefix executes, QProver calls the original compiled:

```solidity
Invariants.checkAll(target)
```

and records `(allHold, firstViolated)` directly.

Static analysis of predicate ASTs is used only for `PropertyFact`, slicing, direction hints, and ranking. Static interpretation is never the runtime truth oracle.

Therefore the two execution boundaries are:

```text
search truth for frontier/ranking = original compiled Invariants.checkAll(target)
final submission proof            = organizer Harness._prove(...)
```

A search-runtime invariant flip is a candidate counterexample. Exit code `0` still requires fresh organizer-Harness reproduction.

## 2. Search runtime must reproduce organizer baseline semantics

Before taking the baseline snapshot, the fast runtime MUST reproduce the organizer-visible baseline as closely as the participant interface permits:

- exact target source bytes;
- exact Solidity and EVM versions;
- manifest block number and timestamp;
- manifest setup/deployment path;
- manifest constructor/value semantics;
- deployed `Invariants.sol` from the supplied source;
- one deployed `SearchAttacker` standing in for the final `Exploit` contract;
- attacker contract funding equal to `Harness.DEFAULT_EXPLOIT_FUNDING_WEI` when the official Harness uses that funding;
- target sees the SearchAttacker contract as `msg.sender` for exploit calls.

Any baseline condition that cannot be reproduced safely is an infrastructure limitation, not a candidate revert and not vulnerability feedback.

## 3. `--max-attempts` accounting

v2.5 MUST NOT use the fast runtime to silently evade the organizer attempt budget.

One **search attempt** is one concrete exploit program executed from an accepted baseline/frontier state and followed by an invariant check. Each such concrete candidate consumes one unit from `--max-attempts`.

The following do not consume a search attempt by themselves, but remain bounded by the global wall-clock budget:

- compiler/static analysis;
- pure getter reads;
- static `eth_call` feasibility probes that do not create an accepted candidate state;
- QUBO/best-first/coverage proposal generation;
- parameter-domain construction.

A final organizer-Harness replay of an already-counted successful concrete candidate is proof confirmation, not permission to discover an additional candidate. If no budget remains for required final proof work, QProver MUST NOT emit exit `0`.

This conservative interpretation preserves the meaning of the official attempt budget while allowing search-internal analysis to become cheaper.

## 4. Candidate and frontier semantics

A candidate is concrete only after parameter completion.

```text
Skeleton != attempt
ConcreteCandidate executed + checkAll == attempt
```

One `Evaluation` MUST correspond to exactly one concrete candidate. The current v2 pattern where an evaluator executes several concrete parameterizations for one skeleton and returns one aggregated `Evaluation` is removed.

If a candidate reverts at step `k`, the executable prefix `[0, k)` may be retained as a frontier state only if QProver can reconstruct or snapshot the exact post-prefix state deterministically. The failed candidate itself remains one consumed attempt.

## 5. Property analysis versus proof semantics

`PropertySlice` may be partial or unknown. Failure to understand an invariant statically MUST NOT cause:

- a false `PROVEN`;
- a safety verdict;
- dropping the invariant from `checkAll`;
- substituting a guessed property implementation.

Unknown static property evidence degrades ranking only. Runtime `checkAll` remains exact.

## 6. Resource-model scope

The v2.5 resource graph is semantic infrastructure, not a disguised vulnerability taxonomy.

P0 resources are limited to facts that can be justified from compiler/runtime evidence:

- contract storage;
- native balance;
- view/getter values;
- action return values;
- external-state placeholders when a call is known but precise state semantics are unknown.

Protocol-specific resource types may be introduced only when derived generically from ABI/compiler/runtime evidence and must not depend on target names, public witnesses, or vulnerability labels.

## 7. Feasibility is state-local

`REVERTS_NOW` means only that a concrete/probe call is infeasible in the current state and parameter context.

It MUST NOT permanently remove the action. The feasibility cache key must include enough state/context identity to avoid learning global statements such as “borrow is bad” from a single precondition failure.

At minimum the feedback identity should include:

```text
(state fingerprint, action id, parameter identity)
```

and may additionally include the predecessor/callback context.

## 8. QUBO scope and performance

QUBO remains one portfolio planner. It operates on a property/resource-filtered action subset and a short active horizon.

P0 MUST include two semantics-preserving performance changes before increasing solver effort:

1. precomputed quadratic adjacency so bit-flip delta is `O(deg(i))` rather than scanning all couplers;
2. sparse transition construction from actual dependency/resource edges rather than dense `A x A` enumeration.

Increasing reads, sweeps, horizon, or attempt count is not an accepted substitute for those changes.

## 9. Fast runtime / SearchAttacker scope

P1 `SearchAttacker` is a persistent generic interpreter-like attacker contract, not a set of vulnerability-specific templates.

Initial supported instructions:

```text
CALL
READ
STORE_TEMP
CALLBACK_PROGRAM
```

The first callback milestone may support native `receive`/`fallback` only. Arbitrary callback selectors are P2.

SearchAttacker bytecode is compiled once per target/toolchain context and reused with snapshot/revert. Candidate-specific Solidity recompilation is not the default search path after Phase 3.

## 10. Final proof boundary

The final organizer Harness remains mandatory even though search uses the original compiled `Invariants.checkAll`.

Reasons include validating:

- exact organizer deployment wrapper;
- exploit funding semantics;
- standalone `Exploit.sol` lowering;
- callback behavior after lowering;
- source/import compatibility;
- final `firstViolated` result.

A mismatch between fast runtime and organizer Harness is treated as a proof failure and must be logged separately from a target-call revert.

## 11. Budget reserve

The runner owns one monotonic deadline beginning before analysis.

Work is divided logically into:

```text
analysis/runtime initialization
search attempts
minimization/final proof reserve
```

The implementation plan must choose an explicit deterministic reserve policy. The policy must guarantee that a candidate discovered near the deadline is not reported as `PROVEN` without enough time for required final Harness validation.

No compiler, planner, verifier, minimizer, or replay subprocess may receive a timeout extending beyond the remaining global deadline.

## 12. Phase gates

### Phase 0 gate — baseline locked

- current v2 branch SHA recorded;
- current six-public-target outcomes recorded;
- current Docker/toolchain identities recorded;
- regression artifacts retained without turning public outcomes into production labels.

### Phase 1 gate — property-directed static planner

Must pass before Phase 2:

- `Invariants.sol` compiler-backed analysis exists;
- every manifest predicate resolves or is explicitly `unknown`;
- `PropertySlice` changes planner relevance on synthetic rename-safe fixtures;
- no vulnerability/target-name branch is introduced;
- sparse QUBO equivalence/performance tests pass;
- iterative/short horizon no longer systematically emits full-length tails on regression fixtures.

### Phase 2 gate — concrete feedback separation

- one concrete candidate equals one evaluation/attempt;
- revert categories preserve candidate versus infrastructure distinction;
- successful prefixes can be represented explicitly;
- state-local feedback does not globally ban a reverting action;
- runtime aliases for identical addresses are canonicalized.

### Phase 3 gate — persistent runtime

- original compiled `Invariants.checkAll(target)` is invoked after search executions;
- SearchAttacker is `msg.sender` for target calls;
- baseline snapshot/revert is deterministic;
- organizer-equivalent funding/time/setup baseline tests pass;
- search default no longer recompiles candidate-specific Solidity.

### Phase 4 gate — contextual parameters

- typed `ValueExpr` lowering round-trips deterministically;
- contextual address binding works without function-name special cases;
- runtime values and Z3 guard models are concrete-replayed;
- parameter feedback is separated from skeleton feedback.

### Phase 5 gate — stateful portfolio

- shared frontier deduplicates equivalent relevant states;
- best-first/QUBO/coverage all consume the same state/action abstraction;
- scheduler is deterministic under the same seed;
- successful-prefix repair is demonstrably used in regression tests.

### Phase 6 gate — proof pipeline

- violating candidate is minimized;
- minimized IR lowers to standalone `Exploit.sol`;
- organizer Harness fresh replay is mandatory for exit `0`;
- official `Exploit.sol`, `attempts.log`, and exit 0/1/2 contract remains valid.

## 13. Acceptance criteria strengthened by self-review

The v2.5 implementation is not considered complete merely because the six public targets pass.

Completion requires all of the following:

- macro-free production search;
- property-directed ranking verified on renamed/metamorphic fixtures;
- original compiled `checkAll` used during fast search;
- final organizer Harness required for success;
- one concrete candidate per attempt/evaluation;
- state-local revert/precondition feedback;
- persistent SearchAttacker runtime in the default search path;
- no candidate-specific full Solidity recompilation in the default search loop;
- short-horizon/iterative planning;
- sparse QUBO delta/transition implementation;
- contextual parameter completion without target/function-name hardcoding;
- execution-backed minimization;
- exact submission-image CI and runtime `--network=none` verification;
- deterministic artifacts for identical input/seed/toolchain;
- no false `PROVEN` on sound controls;
- metamorphic/generalization regressions in addition to public-target regression.

## 14. Self-review result

Placeholder scan: no required design decision is intentionally left `TBD` or `TODO`.

Consistency decision: static property interpretation is a ranking mechanism only; original compiled `Invariants.checkAll` is the search-time invariant oracle, and organizer Harness is the final proof oracle.

Scope decision: proxy/delegatecall recovery, CREATE/CREATE2 general runtime discovery, arbitrary callback selectors, and broad tuple/array support remain P2 so v2.5 can be implemented incrementally.

Implementation should proceed only after this design and its normative self-review are accepted.
