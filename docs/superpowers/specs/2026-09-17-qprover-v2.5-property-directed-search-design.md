# QProver v2.5 — Property-Directed Counterexample-Guided Exploit Synthesis

## 1. 목적

QProver v2.5의 목표는 TRUST404 Track 04에서 공개 타깃의 알려진 취약점 패턴을 직접 인코딩하지 않고도, supplied invariant에서 출발해 관련 상태와 실행 경로를 좁히고, 실제 EVM 실행 피드백을 사용해 executable exploit PoC를 합성하는 것이다.

v2.5는 v2의 macro-free 원칙을 유지하면서 다음 구조적 한계를 해결한다.

1. `Invariants.sol`이 실제 search objective에 충분히 반영되지 않는 문제.
2. reachable contract 전체의 public/external action을 넓게 노출해 QUBO가 잡음 많은 sequence를 선택하는 문제.
3. parameter 생성이 sequence context와 분리되어 `approve(address(this), ...)` 같은 의미적으로 약한 concrete candidate가 생성되는 문제.
4. candidate마다 `Exploit.sol`을 다시 컴파일하고 `forge test`를 실행해 탐색이 느리고, feedback이 `revert_step` 수준으로 축약되는 문제.
5. QUBO가 전역 길이 6 sequence를 한 번에 최적화하면서 long-tail action을 선호하고 model size가 커지는 문제.
6. 기존 QProver core의 persistent EVM evaluator, state fingerprint, coverage search, Z3 parameter solving, minimizer, replay infrastructure를 Track04 경로에서 충분히 재사용하지 못하는 문제.

v2.5의 핵심은 다음 문장으로 요약한다.

> **Property → Resource → State → Feasible Actions → Short-Horizon Planning → Contextual Parameters → Execute → Feedback → Repair → Proof**

성공 판정은 계속 organizer Harness의 실제 invariant violation만 인정한다.

## 2. 비협상 설계 원칙

### 2.1 취약점별 macro 금지

production search 경로에 다음과 같은 vulnerability-class 전용 후보 생성기를 두지 않는다.

- reentrancy macro
- oracle manipulation macro
- access-control macro
- unchecked-accounting macro
- flash-loan macro
- target-name 기반 exploit template

`reentrancy`, `oracle`, `access control` 같은 분류는 성공한 witness를 사람이 설명할 때 사용할 수 있지만 planner의 입력 label이 되어서는 안 된다.

### 2.2 public target 하드코딩 금지

production source에는 public target 이름, expected result, known witness, source hash, known function sequence를 조건으로 하는 분기가 없어야 한다.

### 2.3 Execution is the referee

정적 분석, graph score, QUBO energy, Z3 model, coverage novelty는 후보 우선순위와 parameter 생성에만 사용한다. `PROVEN`은 organizer Harness가 실제로 supplied invariant를 false로 만들었을 때만 출력한다.

### 2.4 Search와 proof 경계 분리

탐색 단계는 빠른 persistent local EVM runtime을 사용한다. 최종 proof 단계는 standalone `Exploit.sol`을 생성하고 organizer Harness에서 fresh validation한다.

```text
fast search runtime != final proof oracle
final proof oracle     = organizer Harness
```

### 2.5 동일 입력의 결정론성

동일 source bytes, manifest, seed, pinned toolchain에서 다음이 안정적으로 고정되어야 한다.

- compiler facts
- property/resource identities
- runtime instance canonicalization
- action ordering
- planner scheduling
- parameter candidate ordering
- attempts.log
- minimized final Exploit.sol

### 2.6 실패는 safety proof가 아님

budget 내에 exploit을 못 찾았다는 사실은 해당 target이 안전하다는 의미가 아니다. exit code `1`은 `NOT_FOUND`, `0`만 executed invariant violation을 의미한다.

## 5. Compiler Frontend

### 5.1 입력

공식 Track04 CLI 계약을 유지한다.

```text
--contract
--invariants
--manifest
--out
--timeout
--seed
--max-attempts
```

### 5.2 compile once

분석용 source closure는 가능한 한 한 번만 compiler build한다.

컴파일 산출물은 다음을 포함한다.

- target source AST/ABI/storage layout
- reachable source closure AST/ABI
- `Invariants.sol` AST/ABI
- optional `Setup.s.sol` source/AST where available
- exact compiler/EVM version identity

analysis workspace와 proof workspace는 분리하되 동일 source bytes와 toolchain identity를 사용한다.

### 5.3 Invariants.sol 분석 추가

v2의 가장 큰 누락을 해결하기 위해 `Invariants.sol`도 compiler-backed property frontend의 입력으로 사용한다.

각 manifest predicate에 대해 `PropertyFact`를 만든다.

```text
PropertyFact
- predicate_name
- function identity
- target-address parameter position
- target getter calls
- native balance reads
- comparison operations where recoverable
- constants
- referenced external views
- source provenance
```

`checkAll()`의 control flow도 분석하여 manifest predicate 이름과 실제 predicate function의 binding을 검증한다. parser가 해석하지 못하는 표현은 fail-open으로 취약하다고 판단하지 않고 `unknown` property evidence로 둔다.

## 6. PropertySlice

### 6.1 목적

Search의 시작점은 vulnerability motif가 아니라 supplied invariant다.

각 predicate `phi`에 대해 backward relevance slice를 만든다.

```text
PropertySlice
- property id
- resource ids
- storage ids
- getter/function ids
- external view dependencies
- target native-balance dependency
- direction hint, if safely recoverable
- provenance
```

### 6.2 slicing 규칙

최소한 다음 관계를 역추적한다.

- predicate가 읽는 target storage/getter
- predicate가 읽는 target native balance
- predicate가 호출하는 target/external getter
- getter가 읽는 storage
- 해당 storage/resource를 write하는 functions
- 해당 functions에 값을 공급하는 upstream resource/actions

### 6.3 property direction

비교 연산을 안전하게 해석할 수 있으면 direction prior를 생성한다.

예:

```text
balance(target) >= SEED
→ healthy side: larger balance
→ violation direction prior: decrease balance
```

이는 proof가 아니라 search prior다.

복잡한 boolean expression, non-monotonic expression, unknown external call은 direction을 `unknown`으로 둔다.

### 6.4 slice 없는 경우

Property frontend가 충분한 정보를 얻지 못해도 search를 중단하지 않는다. 전체 graph를 fallback으로 사용할 수 있으나 property-aware prior가 없는 상태를 명시적으로 기록한다.

## 7. Resource Model

storage-only dependency를 넘어 cross-contract economic/state dependency를 표현한다.

```text
Resource
- STORAGE(storage canonical id)
- NATIVE_BALANCE(runtime contract instance)
- VIEW_VALUE(contract instance, signature, arguments role)
- RETURN_VALUE(action, index)
- APPROVAL_LIKE_STATE where compiler/runtime evidence supports it
- UNKNOWN_EXTERNAL_STATE(call site)
```

특정 token 표준이나 취약점 이름을 전제로 하지 않는다.

resource edges:

```text
Action --reads--> Resource
Action --writes--> Resource
Action --produces--> Resource
Resource --feeds--> Action parameter/guard
Property --reads--> Resource
```

이 graph는 static compiler facts와 runtime observations를 함께 사용할 수 있어야 한다.

## 8. Runtime ContractInstance Graph

### 8.1 문제

v2는 getter path를 action identity 일부로 사용하기 때문에 서로 다른 getter path가 동일 runtime contract address를 가리켜도 중복 action이 생길 수 있다.

### 8.2 ContractInstance

baseline deployment 후 runtime address 기준으로 canonicalize한다.

```text
ContractInstance
- instance_id
- address
- code_hash
- matched compiler artifact, if unique
- discovery_paths
- ABI
- deployment provenance
```

예를 들어 두 getter path가 같은 address를 반환하면 하나의 instance로 합친다.

### 8.3 discovery sources

초기 v2.5 범위에서 다음을 허용한다.

- public storage getter returning contract/interface
- public/external view getter returning address or contract/interface
- target setup에서 이미 배포된 instance
- compiler-resolvable creation result when runtime binding is observable

proxy/delegatecall implementation recovery는 P2로 둔다.

### 8.4 artifact matching

runtime code hash를 compiler artifact runtime bytecode identity와 비교하여 가능한 경우 concrete ABI/analysis facts를 attach한다. ambiguous/no-match는 limited opaque instance로 남긴다.

## 9. Action Model

```text
Action
- id
- contract_instance_id
- function_id
- ABI signature
- parameter types
- payable
- reads/writes resources
- calls/value flows
- role guards/modifiers
- callback capability
- property relevance
- static provenance
```

vulnerability-class `kind`는 두지 않는다.

### 9.1 Feasibility status

각 SearchState에서 action은 다음 상태를 가진다.

```text
FEASIBLE
REVERTS_NOW
UNKNOWN
```

초기 feasibility는 representative argument 또는 parameter completer가 제공한 cheapest probe를 `eth_call`/local execution하여 측정할 수 있다.

`REVERTS_NOW`는 영구 제거를 의미하지 않는다. 이전 action으로 state/authority가 바뀌면 다시 probe할 수 있다.

### 9.2 role guards

`role_guards`, modifier-expanded guard facts, runtime revert evidence를 사용해 초기 priority를 조정하되 guarded action을 영구 제거하지 않는다.

v2.5에서 `analysis.py`에 다음 generic facts를 추가하는 것을 목표로 한다.

- modifier-expanded sender/storage guards
- parameter-to-storage-write flow
- parameter-to-call-argument flow

이 정보는 parameter completer와 state-dependent feasibility에 사용한다.

## 11. SearchState와 Frontier

### 11.1 SearchState

탐색 단위는 단순 sequence가 아니라 execution state다.

```text
SearchState
- state_id
- shortest trace to state
- property observations
- relevant resource observations
- attacker/native/token-like balances where observable
- runtime contract instances
- feasible/reverting action facts
- trace features
- novelty features
- depth
```

### 11.2 state fingerprint

전체 EVM storage hash를 만들 필요는 없다. property/resource relevant observation으로 deterministic fingerprint를 만든다.

동일 fingerprint에 여러 trace가 도달하면 다음 순서로 우선한다.

1. 더 짧은 trace
2. 더 적은 callback complexity
3. 더 단순한 parameters
4. deterministic canonical id

### 11.3 successful prefix 보존

후보가 step `k`에서 revert하면 `[0, k)` prefix가 실행 가능했다는 사실을 frontier에 보존한다.

즉:

```text
A B C D E(revert)
→ A B C D state는 search asset
```

이 정보는 단순 action revert penalty로 축약하지 않는다.

## 12. Search Portfolio

v2.5는 QUBO 하나만 사용하는 runner에서 shared-frontier portfolio로 전환한다.

### 12.1 Best-first / graph planner

property relevance, resource dependency, feasibility, trace length을 기준으로 deterministic short-prefix 탐색을 담당한다.

강점:

- 짧은 exploit
- 명확한 dependency chain
- early feasibility repair

### 12.2 QUBO planner

QUBO는 전체 exploit을 마법처럼 해결하는 backend가 아니라 **현재 state에서 short action ordering을 제안하는 backend**로 제한한다.

기본 rolling horizon은 2~4 actions.

```text
State S
→ relevant feasible action subset
→ QUBO(horizon=2..4)
→ skeleton
→ execute
→ State S'
→ rebuild/reuse QUBO
```

### 12.3 Coverage/state novelty

실행 결과 새로운 trace feature 또는 relevant state fingerprint를 만든 prefix를 corpus에 보존하고 mutation/splice를 수행한다.

### 12.4 scheduler

planner별 고정 quota가 아니라 deterministic adaptive scheduler를 사용한다.

초기 baseline 예:

```text
best-first  : 40%
QUBO        : 40%
coverage    : 20%
```

각 backend가 최근 unique feasible state / non-reverting prefix를 만드는 비율로 quota를 조정할 수 있다. 동일 seed에서는 동일 scheduling이어야 한다.

## 13. Iterative Deepening

global `max_sequence_length=6` objective를 기본 탐색 방식으로 사용하지 않는다.

우선순위는:

```text
depth 1
depth 2
depth 3
...
```

또는 stateful rolling horizon으로 구성한다.

QUBO BQM에서는 가능하면 fixed active horizon을 사용하여 STOP variable/constraint 의존을 줄인다.

장점:

- shortest witness 우선
- BQM size 감소
- length_weight tuning 의존 감소
- 무관한 6-action suffix 방지

## 14. QUBO Performance 개선

### 14.1 sparse flip delta

현재 simulated annealing은 bit flip energy 계산 시 전체 quadratic coefficient를 순회할 수 있다. BQM 생성 시 adjacency를 미리 구성한다.

```text
adjacency[i] = [(j, Qij), ...]
```

flip delta는 `O(deg(i))`, 한 sweep은 sparse graph에서 대략 `O(E)`가 되도록 한다.

### 14.2 sparse transition construction

`A × A` 전체 pair를 순회하기보다 실제 dependency/resource edge가 존재하는 transition만 생성한다.

### 14.3 model telemetry

각 QUBO build에서 최소 다음을 기록한다.

- action count
- horizon
- logical bits
- couplers
- build time
- annealing time
- reads/sweeps
- feasible decoded sample ratio

이를 budget scheduler와 benchmark에 사용한다.

현재처럼 evaluator 하나가 skeleton 내부에서 여러 concrete parameter candidates를 실행한 뒤 하나의 `Evaluation`으로 합치지 않는다.

v2.5 pipeline:

```text
SkeletonPlanner
     ↓
Skeleton
     ↓
ParameterCompleter
     ↓
ConcreteCandidate #1
ConcreteCandidate #2
...
     ↓
각각 독립 Evaluation
```

SearchController의 one evaluation은 one concrete candidate execution과 1:1 대응해야 한다.

planner feedback과 parameter feedback도 분리한다.

## 16. Parameter Completer

### 16.1 ValueExpr

parameter를 raw literal 목록이 아니라 typed expression으로 표현한다.

```text
ValueExpr
- Const(v)
- SelfAddress
- TargetAddress
- ContractAddress(instance)
- ReadUint(instance, signature, args)
- PreviousReturn(step, index)
- Scale(expr, numerator, denominator)
- Add/Sub(expr, expr)
- Min/Max(expr, expr)
```

모든 expression은 deterministic lowering이 가능해야 한다.

### 16.2 source priority

parameter candidates는 다음 순서에서 생성한다.

1. exact context-derived value
2. current runtime resource value
3. previous action return/observation
4. source constant
5. bounded ABI boundary
6. deterministic fallback actors

### 16.3 contextual address binding

address argument는 sequence context를 반영한다.

일반 rule 예:

```text
current action의 address argument
→ next action target instance
→ previous producing instance
→ self
→ root target
→ other reachable instances
→ fixed other actor
```

특정 function 이름을 검사해 `approve` 전용 macro를 만드는 방식은 금지한다. parameter-to-call/resource analysis와 next consumer relationship으로 우선순위를 만든다.

### 16.4 integer constraints + Z3

compiler가 `require/assert`에서 안전하게 추출한 bounded integer constraints는 기존 `parameters.py`의 Z3 solver에 연결한다.

Z3는 전체 EVM symbolic execution이 아니라 parameter completion에만 사용한다.

모든 Z3 model은 concrete EVM 실행으로 재검증한다.

### 16.5 mutation dictionary

runtime feedback에서 얻은 다음 값을 deterministic dictionary에 추가한다.

- getter values
- balances
- successful arguments
- near-boundary values
- decoded revert/custom-error arguments where available

## 17. Generic SearchAttacker Runtime

### 17.1 목적

candidate마다 standalone Solidity를 다시 컴파일하지 않고, official attacker contract semantics에 가까운 persistent attacker runtime을 한 번 배포한다.

### 17.2 요구사항

SearchAttacker는 최소 다음 instruction을 지원한다.

```text
CALL(instance, signature, ValueExpr[], value)
READ(instance, signature, ValueExpr[])
STORE_TEMP(slot, result)
CALLBACK_PROGRAM(id, instruction sequence)
```

### 17.3 msg.sender semantic consistency

search runtime에서 target이 보는 `msg.sender`는 EOA가 아니라 SearchAttacker contract여야 한다. final `Exploit.sol`에서도 동일 역할을 가진다.

### 17.4 snapshot/revert

baseline setup 후 Anvil snapshot을 만들고 candidate마다:

```text
revert baseline snapshot
→ candidate execute
→ collect observations/trace/revert
```

또는 frontier state snapshot을 별도로 관리한다.

### 17.5 fallback/receive

SearchAttacker는 generic callback dispatcher를 가진다. callback은 동일 action 반복으로 고정하지 않는다.

```text
CallbackProgram
- trigger context
- allowed sender/callsite evidence
- instruction sequence
- depth budget
```

초기 구현은 native receive/fallback callback부터 시작하고 arbitrary selector callback은 후속 단계에서 확장할 수 있다.

## 18. Execution Feedback

### 18.1 결과 category

다음을 명확히 구분한다.

```text
PROVEN
PASS
CANDIDATE_REVERT
PARAMETER_INVALID
CODEGEN_ERROR
COMPILE_ERROR
SETUP_ERROR
HARNESS_ERROR
TIMEOUT
INFRA_ERROR
```

compile/infrastructure 오류를 exploit-search revert penalty에 넣지 않는다.

### 18.2 revert data 보존

SearchAttacker와 final Exploit renderer 모두 가능한 경우 raw revert bytes를 보존한다.

feedback 최소 형태:

```text
revert_step
revert_selector
revert_kind
raw_revert_hash
```

human-readable reason은 optional이며 deterministic log에는 normalized stable form만 기록한다.

### 18.3 state-local feedback

`borrow` 자체를 global하게 penalize하지 않는다.

```text
(State S, previous action/context, failing action)
```

단위로 infeasibility를 기록한다.

### 18.4 positive feedback

다음은 우선순위를 높인다.

- previously reverting action becomes feasible
- relevant resource changed
- property observation moved toward violation direction
- new state fingerprint
- new cross-contract call edge observed

## 20. Minimization

Search에서 invariant violation이 확인되면 official proof 전에 witness를 최소화한다.

1. violating prefix truncate
2. ddmin contiguous chunk removal
3. single-step deletion fixed point
4. callback depth reduction
5. parameter simplification
6. runtime expression simplification
7. final fresh fast-evaluator check
8. standalone `Exploit.sol` render
9. organizer Harness fresh check

기존 `minimizer.py`의 실행 기반 구조를 최대한 재사용하되 Track04 `ValueExpr`/callback instruction을 처리할 domain adapter를 추가한다.

최소화가 budget을 과도하게 소비하지 않도록 search budget과 proof/minimization reserve를 분리한다.

## 21. Organizer Harness Final Proof

최종 성공 경계는 바꾸지 않는다.

```text
minimized Exploit.sol
        ↓
original Target.sol / Invariants.sol / Setup
        ↓
Organizer Harness._prove
        ↓
PROVEN + firstViolated
```

fast search runtime에서 invariant가 깨졌더라도 official Harness가 재현하지 못하면 exit `0`을 반환하지 않는다.

개발/CI 모드에서는 successful public witness를 organizer Harness에서 반복 replay하여 determinism evidence를 수집할 수 있다.

## 22. Budget Model

전체 wall-clock budget은 process start부터 적용한다.

권장 내부 배분은 hard partition이 아니라 reserve를 둔다.

```text
analysis/runtime initialization: bounded
search:                     majority budget
proof/minimization reserve: protected tail budget
```

최소 보장:

- deadline 이후 새 compiler/verifier/search backend 작업 시작 금지
- planner의 단일 `propose()`가 전체 deadline을 무한히 점유하지 못함
- QUBO backend는 caller-provided deadline/budget을 확인 가능해야 함
- final proof reserve가 없다면 `FOUND_FAST`를 `PROVEN`으로 승격하지 않음

## 24. QUBO의 정확한 역할

v2.5는 다음을 주장하지 않는다.

- NP-hard QUBO를 polynomial time에 해결한다.
- simulated annealing이 global optimum을 보장한다.
- quantum advantage가 존재한다.

QUBO의 역할은:

> property/resource/state로 좁혀진 discrete action-ordering 문제에 static dependency와 runtime feedback을 하나의 optimization objective로 결합해 short-horizon sequence를 우선순위화하는 것.

QUBO의 효용은 portfolio ablation으로 검증한다.

## 30. Acceptance Criteria

v2.5 architecture implementation은 다음 조건을 만족해야 완료로 간주한다.

### Architecture

- production path에 vulnerability-specific macro가 없음
- supplied invariant가 실제 planner relevance에 사용됨
- runtime state/frontier가 search input으로 사용됨
- QUBO는 short-horizon planner이며 proof oracle이 아님
- one evaluation = one concrete candidate

### Soundness

- organizer Harness violation 없이 exit 0 없음
- compile/infra failure가 vulnerability feedback으로 학습되지 않음
- safe controls에서 false PROVEN 없음

### Generalization

- public target 이름/known sequence 조건 없음
- semantic/metamorphic rename/wrapper 변화에 대한 regression 존재
- cross-contract runtime alias가 canonicalized됨

### Performance

- candidate마다 Solidity full recompile을 search default로 사용하지 않음
- QUBO annealing sparse flip-delta optimization 적용
- analysis/search/final proof가 하나의 wall-clock deadline을 존중

### Proof

- found witness를 최소화
- minimized standalone `Exploit.sol`이 organizer Harness에서 fresh replay됨
- official outputs `Exploit.sol`, `attempts.log`, exit 0/1/2 계약 유지

### Reproducibility

- submission Docker와 submission CI toolchain 일치
- Python lockfile 실제 강제
- `--network=none` runtime 통과
- 동일 seed/input에서 deterministic artifacts

## 32. 최종 설계 결정

QProver v2.5는 기존 v2에 public-target heuristic을 계속 추가하는 방향을 선택하지 않는다.

최종 선택은 다음과 같다.

> **Property-Directed Counterexample-Guided Portfolio Exploit Synthesizer**

- Property가 relevance를 결정한다.
- Resource graph가 cross-contract dependency를 연결한다.
- Runtime state가 feasibility를 결정한다.
- Best-first/QUBO/Coverage가 short-horizon 후보를 제안한다.
- Parameter completer가 context/runtime/Z3로 concrete values를 만든다.
- SearchAttacker가 빠르게 실행하고 state/revert feedback을 반환한다.
- Successful prefix와 novel state를 frontier에 보존한다.
- 실행된 counterexample이 발견되면 최소화한다.
- Organizer Harness가 최종 proof를 결정한다.

이 구조는 v1의 public-target macro 성능을 재현하는 것이 목표가 아니라, hidden target에서 취약점 이름을 모르는 상태에서도 supplied invariant를 실제로 깨뜨리는 witness를 찾을 가능성을 높이는 것을 목표로 한다.
