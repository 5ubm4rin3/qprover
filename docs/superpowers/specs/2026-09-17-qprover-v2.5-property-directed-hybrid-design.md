# QProver v2.5 — Property-Directed Hybrid Exploit Synthesis Design

Date: 2026-09-17  
Baseline: `feat/qprover-v2-generalized-search` at `2e5b0a300e2a5fe029da225a36d111af1af688e6`

## 1. Purpose

QProver v2.5 turns the current macro-free Track 04 prototype into a property-directed, execution-guided exploit synthesizer that can generalize beyond the public target set without reintroducing vulnerability-class macros.

The core objective is:

> Given the organizer-provided target, invariants, manifest, deterministic deployment environment, and bounded budget, synthesize an executable exploit that causes at least one supplied invariant predicate to become false, and accept success only after the organizer Harness reproduces the violation.

The design preserves the strongest parts of the existing project:

- compiler-backed Solidity analysis;
- typed program/dependency graph;
- generic search infrastructure;
- QUBO/BQM backend;
- local EVM execution infrastructure;
- deterministic budgets and evidence;
- minimization and replay machinery;
- organizer-compatible `Exploit.sol`, `attempts.log`, and exit codes.

The main change is architectural: the Track 04 path must stop treating search as a mostly static ranking problem over all reachable ABI functions and instead become a property-directed state search with explicit runtime feedback.

## 2. Hard design constraints

The following are non-negotiable.

### 2.1 No vulnerability-class macros

Production Track 04 search must not contain dedicated exploit candidates, renderer branches, or planner labels such as:

- reentrancy macro;
- access-control macro;
- oracle manipulation macro;
- unchecked-accounting macro;
- public-target-specific sequences;
- target-name or expected-answer special cases.

Generic capabilities are allowed and required. Examples include generic callback dispatch, generic dynamic contract discovery, generic storage/resource dependencies, generic runtime reads, bounded SMT parameter completion, and generic state-aware repair.

### 2.2 Execution is the final referee

Static analysis, graph ranking, QUBO energy, solver satisfiability, and search novelty are candidate-generation signals only. They must never independently produce `PROVEN`.

Only an actual organizer Harness execution that reports an invariant violation may produce exit code `0`.

### 2.3 Same inputs, seed, and toolchain must remain deterministic

The following must be stable under a fixed environment:

- compiler-derived facts;
- runtime contract-instance discovery order;
- property slices;
- action ordering;
- parameter candidate ordering;
- planner scheduling;
- QUBO construction and seeded annealing;
- state-frontier tie breaking;
- generated exploit source;
- attempts log formatting.

Wall-clock durations are not part of deterministic artifacts.

### 2.4 Official Track 04 boundary remains unchanged

The CLI remains:

```text
--contract
--invariants
--manifest
--out
--timeout
--seed
--max-attempts
```

The output remains:

```text
Exploit.sol
attempts.log
```

Exit codes remain:

```text
0 = proven invariant violation
1 = not found within budget
2 = input/infrastructure/internal error
```

## 3. Diagnosis of the current v2 implementation

The current v2 implementation established several necessary foundations but does not yet implement the full design written in the original v2 spec.

### 3.1 What already works and should be retained

- `trust404_analysis.py` compiles the organizer source closure and reuses `analysis.py` / `graph.py`.
- reachable contract-typed storage getters are followed across contracts;
- compiler-generated public getters are retained in auxiliary contract ABI data;
- target and reachable auxiliary public/external state-changing functions become generic actions;
- runtime address and uint getter expressions can be lowered into `Exploit.sol`;
- callback-capable actions exist without a reentrancy-specific macro;
- parameter variants are separated from action-level QUBO skeleton search;
- Harness failures can report `revert_step=N`;
- local `solc 0.8.24` is pinned for offline execution;
- public sound controls have not produced false `PROVEN` results in observed runs.

### 3.2 Main architectural gap

The current Track 04 path still behaves approximately as:

```text
compiler facts
    ↓
all reachable public/external functions
    ↓
static semantic utility
    + storage-overlap transition score
    ↓
QUBO action skeleton
    ↓
bounded parameter variants
    ↓
compile Exploit.sol
    ↓
Harness result
```

The supplied invariant does not yet materially constrain the action universe or objective. The state reached by a successful prefix is not retained as a first-class frontier state. Runtime feedback is mostly reduced to action-level revert penalties. Candidate verification recompiles Solidity for each attempt.

The result is predictable: the system is macro-free, but it can still rank long semantically noisy sequences because it does not yet understand which resources the property depends on or which states make an action feasible.

## 5. Compiler frontend

### 5.1 One compiler closure for target semantics

The existing compiler-backed target frontend remains the source of truth for target and reachable source semantics.

It must retain:

- compact AST;
- ABI;
- method selectors;
- storage layout;
- source spans;
- contract identities;
- function identities;
- read/write/call/value-flow facts.

No Solidity regex parser may replace compiler facts for semantic decisions.

### 5.2 Invariants must also be analyzed as code

The current v2 checks that `Invariants.sol` exists but does not make it a first-class search input. v2.5 must compile/analyze the invariant contract and construct a property model for every predicate listed in `manifest.invariants.predicates`.

A property model does not need full formal EVM semantics. It should extract the strongest sound information available and treat unknown portions as unknown, not as proof of safety or vulnerability.

## 6. Property model and PropertySlice

Each organizer predicate becomes a `PropertySlice`.

Conceptual shape:

```text
PropertySlice
- predicate name
- predicate function identity
- target/environment resources read
- target getters called
- auxiliary getters called
- storage/resources transitively affecting those reads
- relevant function/action identities
- comparison/direction facts when safely recoverable
- provenance
```

### 6.1 Resource examples

The property layer must be broader than Solidity storage slots. Generic resource kinds include:

```text
STORAGE(contract, slot/id)
NATIVE_BALANCE(address-expression)
VIEW_VALUE(contract-instance, getter, args)
TOKEN_BALANCE(contract-instance, account-expression)
ALLOWANCE(contract-instance, owner-expression, spender-expression)
RETURN_VALUE(call-site)
ENVIRONMENT(block.number / timestamp when observed)
```

Token-like resources are semantic abstractions over compiler/runtime call structure, not vulnerability classes.

### 6.2 Backward slicing

Property slicing starts from predicate reads and walks backward through:

- target getter calls;
- storage read dependencies;
- internal call dependencies;
- reachable external getter/value dependencies where resolvable;
- functions that write a relevant resource;
- functions that write resources read by other relevant functions.

The output is a relevance prior, not a soundness theorem.

### 6.3 Property direction

When a predicate has a safely understandable comparison, record a directional objective.

Examples:

```text
balance(target) >= SEED
→ violation direction: decrease balance(target)

owner(target) == initial_owner
→ violation direction: make owner differ

assets >= liabilities
→ violation direction: reduce assets or increase liabilities
```

If direction is not reliably recoverable, omit it and retain only dependency relevance.

## 7. Program graph to Resource Graph

The current graph is storage-centric and remains useful, but v2.5 adds resource-level edges.

Each action may have:

```text
reads(resources)
writes(resources)
produces(resources)
consumes(resources)
approves(resources)
calls(contract instances)
requires(guards/preconditions)
```

Generic transition evidence includes:

```text
A writes R, B reads R        → A → B
A produces R, B consumes R   → A → B
A changes R, property reads R → property relevance
A returns address used as B target → address dependency
A establishes allowance/resource needed by B → execution dependency
```

The planner must operate on these dependencies rather than only same-contract storage overlap.

## 8. Runtime ContractInstance model

Static getter paths are discovery evidence, not final identity.

At baseline deployment, evaluate discovered address getters and canonicalize runtime contracts as:

```text
ContractInstance
- runtime address
- code hash
- matched compiler artifact if known
- ABI
- discovery paths
- parent instances
- provenance
```

If both:

```text
target.borrowToken()
target.pool().bor()
```

resolve to the same runtime address/code, they are one `ContractInstance` with multiple discovery paths.

This prevents duplicate action universes and permits state-aware target identity.

### 8.1 Dynamic address discovery

Discovery sources may include:

- public contract/interface typed storage getters;
- public/external view getters returning address/contract values;
- compiler-resolved created contracts;
- runtime-observed call destinations when their code matches an analyzed artifact.

Unknown external code remains an opaque instance unless a trusted ABI/artifact is available.

## 9. State-aware attacker action model

A generic action is identified by runtime contract instance plus ABI call semantics.

```text
Action
- id
- contract instance
- function identity/signature
- parameter types
- payable
- resources read
- resources written
- external calls
- value flows
- guards/preconditions
- callback capability
- property relevance
- provenance
```

No vulnerability-class `kind` field is introduced.

### 9.1 Feasibility is state-dependent

Public/external does not imply currently attacker-callable.

For a given search state, classify representative calls as:

```text
FEASIBLE
REVERTS_NOW
UNKNOWN
```

A guarded action is not permanently deleted. A prior action may change ownership, allowance, debt, balance, or another precondition and make it feasible later.

This avoids both extremes:

- treating every public function as immediately usable;
- permanently filtering guarded functions that can become reachable after state changes.

## 10. Generic SearchAttacker runtime

Repeated compilation of a new `Exploit.sol` per search attempt is too expensive and discards rich execution feedback.

v2.5 introduces one generic attacker runtime used only during search.

Conceptual interface:

```text
SearchAttacker.execute(program, target)
```

The attacker executes a compact instruction program containing operations such as:

```text
READ_ADDRESS
READ_UINT
CALL
STORE_TEMP
SCALE
CALLBACK_SET_PROGRAM
CALLBACK_CLEAR
```

This attacker is compiled/deployed once per target baseline.

### 10.1 Semantic equivalence requirement

Search execution must match final exploit semantics where relevant:

- target sees the attacker contract as `msg.sender`;
- attacker owns its token balances/allowances;
- attacker receives the same Track 04 exploit funding policy;
- callback execution occurs through the attacker contract;
- block number/timestamp match the manifest.

### 10.2 Snapshot execution

Search loop:

```text
establish deterministic baseline
→ deploy SearchAttacker
→ create EVM snapshot
→ execute candidate
→ collect feedback
→ revert snapshot
→ execute next candidate
```

Final organizer proof remains a fresh independent Harness execution.

## 11. Callback program abstraction

The current callback mode repeats the same action in `receive()`. v2.5 generalizes this to a callback program without introducing reentrancy-specific logic.

```text
CallbackProgram
- trigger action
- callback instruction sequence
- callback source constraints when needed
- maximum depth/hops
```

Example shapes the abstraction can express:

```text
A → callback(A)
A → callback(B)
A → callback(B → C)
```

The callback dispatcher may key on sender, selector/context, and depth, but planner inputs remain generic program semantics.

## 12. SearchState and frontier

Search is over states, not only complete sequences.

```text
SearchState
- deterministic state signature
- shortest known trace
- property observations
- relevant resource observations
- feasible/reverting action facts
- trace features
- dynamic contract instances
- parameter dictionary additions
- novelty/progress score
```

### 12.1 State signature

The signature should hash only deterministic, security-relevant observations available to the search runtime, such as:

- property-relevant getter values;
- relevant native balances;
- relevant token/resource values;
- discovered contract addresses/code identities;
- selected execution trace features.

It must not require full EVM storage cloning.

### 12.2 Dominance

If two traces reach the same relevant state signature, retain the shorter/lower-cost trace. Longer dominated traces do not remain in the active frontier.

### 12.3 Successful prefixes are first-class evidence

For a candidate:

```text
A → B → C → D → E(revert)
```

`A → B → C → D` is a useful reachable state and must be retained rather than collapsed into one penalty on `E`.

This is the core counterexample-guided repair mechanism.

## 13. Search portfolio

QProver v2.5 uses a deterministic portfolio sharing one state frontier.

### 13.1 Best-first / graph search

Use property relevance, dependency distance, feasibility, novelty, and trace length to prioritize short semantic paths.

This is the primary mechanism for exploiting explicit program/resource dependencies.

### 13.2 QUBO-guided local ordering

QUBO remains a first-class backend but receives a smaller, state-conditioned problem.

Instead of global action-space horizon 6:

```text
current SearchState
→ property-relevant feasible/near-feasible actions
→ short horizon 2–4
→ QUBO proposes local action ordering
```

QUBO remains a prioritizer, not a solver oracle.

### 13.3 Coverage/state novelty mutation

Reuse and adapt the existing coverage-guided infrastructure to mutate successful prefixes and states that produced new trace/state features.

This provides escape from incomplete static dependency modeling.

### 13.4 Deterministic scheduling

The portfolio scheduler must be deterministic under a seed. A suggested initial schedule is weighted round-robin rather than wall-clock racing so reproducibility does not depend on thread timing.

## 14. Iterative depth instead of global fixed-length preference

Global six-position sequence optimization caused repeated six-action candidates even after length penalties were increased.

v2.5 uses iterative depth / rolling horizon:

```text
depth 1
→ depth 2
→ depth 3
→ depth 4 when justified
```

For QUBO this reduces logical bits, removes pressure to tune a global sequence-length reward, and naturally prioritizes shorter exploits.

The STOP encoding can remain in generic BQM infrastructure for compatibility, but the Track 04 planner should prefer exact local horizons when practical.

## 15. QUBO/BQM performance improvements

The current simulated annealer computes a bit-flip energy delta by scanning all quadratic couplers for every bit. This is unnecessarily expensive for larger models.

v2.5 should precompute adjacency/local fields so a flip costs proportional to the variable degree rather than the entire coupler set.

Target complexity improvement:

```text
current sweep: approximately O(n * E)
preferred sweep: approximately O(E)
```

where `n` is the number of logical variables and `E` is the number of quadratic couplers.

BQM construction should also iterate sparse nonzero transitions rather than all action-pair combinations where possible.

These changes must preserve exact BQM energy semantics and deterministic seeded behavior.

## 16. SkeletonPlanner and ParameterCompleter separation

One planner proposal must no longer hide multiple concrete Harness attempts inside one evaluator result.

New separation:

```text
SkeletonPlanner
    ↓
ParameterCompleter
    ↓
ConcreteCandidate
    ↓
SearchEvaluator
    ↓
Feedback
  ↙        ↘
planner   completer
```

One evaluation corresponds to one concrete candidate.

This makes:

- candidate budgeting exact;
- parameter-specific failures visible;
- feedback attribution correct;
- attempts logging straightforward;
- comparison across planners fair.

## 17. Typed ValueExpr parameter language

Runtime parameter references should become a typed internal expression language.

Conceptual forms:

```text
Const(value)
SelfAddress
TargetAddress
ContractAddress(instance)
ReadUint(instance, getter, args)
PreviousReturn(index)
Scale(expr, numerator, denominator)
Add(expr, expr)
Sub(expr, expr)
Min(expr, expr)
Max(expr, expr)
```

Every expression records provenance.

### 17.1 Contextual address binding

Address parameters should use call-sequence context.

Generic examples:

```text
an address parameter followed by a call to instance P
→ P is a high-priority candidate

self-account indexed getter
→ attacker address is a high-priority candidate
```

No function-name-specific `approve` exploit macro is required. ABI semantics and parameter/data-flow evidence may raise or lower candidates when compiler facts support it.

### 17.2 Runtime integer seeds

Integer candidates may come from:

- ABI boundaries;
- manifest deployment values;
- attacker/target balances;
- getter observations;
- property constants;
- source constants;
- prior return values;
- prior successful parameters;
- simple deterministic scales and arithmetic.

## 18. Guard/constraint extraction and Z3 completion

The existing core Z3 parameter solver should be reused instead of maintaining an isolated Track 04 parameter engine indefinitely.

Compiler analysis should extract supported scalar constraints from `require` / `assert` / simple branch guards when their data dependencies are understood.

Examples:

```text
amount <= balance
amount > 0
debt + amount <= collateral * price / SCALE
msg.value == amount
```

Supported constraints are translated into bounded models, solved deterministically, and concretely revalidated before use.

Unsupported EVM/Solidity semantics are not guessed; the completer falls back to deterministic runtime values/mutations.

## 19. Analysis improvements required for v2.5

The compiler fact layer should grow in generic ways that improve planning and parameter completion:

- modifier-expanded role/guard dependencies;
- parameter-to-storage assignment flows;
- parameter-to-external-call argument flows;
- parameter-to-call-receiver flows;
- return-value dependencies;
- explicit native-balance reads where detectable;
- simple require/assert expression representation;
- external call argument/receiver identities when compiler evidence resolves them.

Existing heuristic names such as oracle/token may remain in legacy core compatibility paths, but the v2.5 Track 04 planner must not depend on vulnerability taxonomy labels.

## 20. Runtime feedback taxonomy

Search feedback must distinguish candidate behavior from infrastructure behavior.

Required categories:

```text
PROVEN
PASS
CANDIDATE_REVERT
CANDIDATE_TIMEOUT
CODEGEN_ERROR
COMPILE_ERROR
SETUP_ERROR
HARNESS_ERROR
INFRA_ERROR
```

Only candidate-level outcomes may train search feasibility/parameter feedback.

Infrastructure/codegen failures must never be interpreted as evidence that an action or transition is semantically bad.

## 21. Preserve raw revert evidence

The generic attacker/final renderer should retain original revert data instead of replacing every failure with only a step number.

Internal feedback should record, when available:

```text
failing step
raw revert bytes
Error(string) selector/message hash or normalized message
Panic code
custom-error selector
empty revert
```

Deterministic artifacts should normalize or hash unstable textual output.

Search learns state/prefix-specific failure facts rather than global function invalidity.

## 22. Feedback semantics

Feedback must be contextual.

Avoid:

```text
borrow reverted once → borrow is bad globally
```

Prefer:

```text
state S + prefix P + action borrow + parameter set X → revert
```

Useful feedback objects include:

```text
FeasibilityFact(state_signature, action, status)
TransitionFact(state_signature, previous_action, action, outcome)
ParameterFact(state_signature, action, argument_position, value_expr, outcome)
PrefixFact(trace, resulting_state_signature)
```

The QUBO backend may consume an aggregated deterministic projection of these facts while the frontier retains the full contextual form.

## 23. Invariant progress feedback

When a property exposes numeric or comparable observations, search should record progress toward violation.

Examples:

```text
balance threshold distance decreased
debt/assets ratio moved toward failure
owner value changed away from baseline
```

This is not a proof metric and must never fabricate direction when the predicate is opaque.

If only boolean `checkAll` is available, the system still uses resource/state novelty and dependency relevance.

## 24. Search-time evaluator vs proof-time verifier

v2.5 explicitly separates two trust roles.

### 24.1 SearchEvaluator

Purpose:

- fast repeated candidate execution;
- snapshots/reverts;
- trace/resource observations;
- state signatures;
- revert data;
- feasibility feedback.

It may use QProver-owned Anvil and `SearchAttacker`.

### 24.2 OfficialVerifier

Purpose:

- final organizer semantics;
- original target/invariants/setup;
- standalone generated `Exploit.sol`;
- exact Track 04 Harness;
- authoritative `PROVEN` / `NOT_PROVEN`.

A search-time violation must be re-rendered and re-proven with `OfficialVerifier` before exit `0`.

## 25. Minimization

The existing execution-backed minimizer should be adapted to the Track 04 concrete-candidate domain.

After search finds a candidate violation:

```text
violation candidate
→ remove irrelevant suffix after first violation
→ ddmin contiguous chunks
→ single-step deletion fixed point
→ simplify callback program when possible
→ simplify arguments/value expressions
→ fresh search-runtime replay
→ render final Exploit.sol
→ fresh organizer Harness proof
```

If minimization loses the official violation, retain the last officially proven candidate.

## 26. Final Exploit lowering

The final standalone exploit is generated from a generic Exploit IR, not vulnerability-specific source templates.

IR examples:

```text
READ_ADDRESS
READ_UINT
CALL
SET_CALLBACK_PROGRAM
CLEAR_CALLBACK_PROGRAM
```

Final Solidity may contain generic runtime helpers:

- address/getter readers;
- uint readers;
- arithmetic helpers;
- callback dispatcher;
- structured failure instrumentation for development builds.

The published successful `Exploit.sol` may remove search-only instrumentation if doing so is reverified by the official Harness.

## 27. Budget model

The user/organizer timeout is one end-to-end wall-clock budget covering:

```text
manifest validation
compiler analysis
property/resource construction
runtime setup
search
parameter completion
candidate execution
minimization
final official verification
output writing
```

Before every expensive operation, calculate remaining budget and fail closed when insufficient.

`--max-attempts` counts concrete exploit candidates that receive candidate execution/proof work. Internal QUBO reads or graph expansions do not consume attempt count.

Search and final proof budgets should reserve a small deterministic tail for final official verification once a search-time violation is found.

## 28. Deterministic portfolio scheduling

Concurrency must not make result ordering nondeterministic.

Initial v2.5 should use deterministic interleaving:

```text
best-first quota
→ QUBO quota
→ coverage quota
→ repeat
```

Each strategy receives deterministic frontier snapshots and tie-break rules. Parallel execution can be evaluated later only if result commitment order is made independent of completion timing.

## 29. Reproducible toolchain

Submission CI must test the actual submission environment, not only the developer environment.

Required alignment:

```text
Python version used by Docker
Foundry version used by Docker
solc version used by organizer manifest
EVM version
Python dependency lock
forge-std revision
```

The Docker build should install Python dependencies from the locked environment rather than copying `uv.lock` and then resolving independently with unrestricted `pip install .`.

CI must include an exact-Docker job that:

```text
builds linux/amd64 image
runs with --network=none
checks tool versions
runs focused Track04 tests
runs public targets under official CLI
```

## 30. Public-target policy

Public targets are regression tests, not planner knowledge.

Allowed:

- asserting that generic semantics can express their exploit;
- using their failures to reveal generic architectural gaps;
- holding them as integration tests.

Forbidden:

- target names in production search logic;
- known exploit action sequences as priors;
- vulnerability family labels selecting candidate generators;
- hardcoded public invariant names or expected exits.

A patch is preferred when it improves a generic semantic capability and can be tested with an abstract fixture independent of a public target.

## 31. Generalization benchmark

The existing v1 microbenchmark remains historical evidence for QUBO prioritization only.

v2.5 needs a separate benchmark focused on structural generalization.

Recommended benchmark construction:

- family holdout where possible;
- renamed functions/storage/contracts;
- reordered source declarations;
- equivalent wrapper contracts;
- extra irrelevant public functions;
- alias getters leading to the same runtime contract;
- guarded decoy actions;
- callback variants;
- perturbed constants/balances;
- safe twins.

Report at minimum:

```text
confirmed positive rate
false PROVEN rate
attempts to first proof
wall time to first proof
search-runtime candidates/sec
QUBO logical bits/couplers/time
state-frontier size
unique runtime states
revert-prefix reuse rate
```

## 32. Testing strategy

### 32.1 Compiler/property unit tests

- predicate resource extraction;
- native balance property extraction;
- getter/transitive storage slicing;
- modifier guard propagation;
- parameter/resource flow extraction;
- unknown predicate constructs fail conservatively.

### 32.2 Runtime instance tests

- alias getter paths deduplicate by runtime address/code;
- dynamic address-return getters are discovered;
- unknown external instances remain opaque;
- action identities remain deterministic.

### 32.3 Frontier tests

- successful prefix is retained after later revert;
- shorter trace dominates longer trace with same state signature;
- same action can be infeasible in one state and feasible in another;
- contextual revert does not globally ban an action.

### 32.4 Planner tests

- property-irrelevant actions receive lower priority;
- iterative depth prefers a valid short path over a rewarded irrelevant tail;
- QUBO local horizons remain deterministic;
- sparse BQM optimization preserves exact energy/sample ordering under fixed seed for controlled fixtures.

### 32.5 Parameter tests

- contextual contract-address binding;
- runtime getter expressions;
- previous-return values;
- bounded arithmetic expressions;
- supported guard constraints solved by Z3 and concretely revalidated;
- unsupported constraints fail conservatively.

### 32.6 Callback tests

- same-action callback;
- different-action callback;
- multi-step callback;
- callback depth bound;
- unrelated ERC20-style external calls do not automatically create native callback paths.

### 32.7 Official proof tests

- only organizer Harness can cause final success;
- search-time false positive is rejected by final verifier;
- minimized exploit is freshly re-proven;
- sound controls never exit `0`.

### 32.8 Budget tests

- compilation respects global deadline;
- search does not start work after deadline;
- final proof reserves/uses remaining time correctly;
- concrete attempt counting is exact.

### 32.9 Submission-image tests

- exact Docker versions;
- offline build/runtime;
- no network dependency;
- public targets deterministic across repeated runs.

## 33. Implementation boundaries

The following existing modules should be preserved and extended rather than rewritten without cause:

```text

graph.py
search/bqm.py
search/qubo.py
search/coverage.py
search/risk.py
search/controller.py
parameters.py
minimizer.py
evm.py
evaluator.py
```

Track 04-specific orchestration should become thinner over time.

Suggested new focused modules:

```text
trust404_property.py      # invariant compilation/model/slicing
trust404_resources.py     # resource/action dependencies
trust404_instances.py     # runtime contract discovery/canonicalization
trust404_runtime.py       # baseline/SearchAttacker/snapshot evaluator
trust404_frontier.py      # SearchState / dominance / feedback facts
trust404_parameters.py    # ValueExpr and contextual completion adapter
trust404_planner.py       # deterministic portfolio coordination
trust404_ir.py            # generic exploit IR/final lowering
```

Names may change during planning, but responsibilities must remain separated.

`trust404.py` should not continue growing into a monolithic analyzer, parameter engine, planner, and renderer.

## 34. Migration phases

### Phase 0 — freeze and instrument current baseline

- preserve current v2 branch as comparison baseline;
- add stable metrics for model size, attempts, and timing;
- retain current public results as regression evidence.

### Phase 1 — property/resource foundation

- compile/analyze invariants;
- implement PropertySlice;
- introduce generic resources;
- property-directed action relevance;
- iterative-depth planner input.

This phase should already reduce noisy six-action sequences without target-specific rules.

### Phase 2 — QUBO core efficiency

- sparse adjacency flip delta;
- sparse transition construction;
- deterministic equivalence tests;
- rolling local horizons.

### Phase 3 — runtime instances and feasibility

- baseline deployment runtime discovery;
- alias deduplication;
- state-dependent feasibility probes;
- contextual action activation.

### Phase 4 — SearchAttacker and state frontier

- compile/deploy generic search attacker;
- Anvil snapshot/revert evaluation;
- state signatures;
- successful-prefix frontier;
- contextual feedback.

## 35. Success criteria

v2.5 architecture is considered implemented when all of the following hold:

1. Production Track 04 code contains no vulnerability-class macros or public-target-specific exploit sequences.
2. Every planner run is seeded from at least one actual `PropertySlice` or an explicit conservative fallback when property parsing is opaque.
3. Runtime contract aliases are canonicalized by actual deployed identity.
4. Search retains successful prefixes as state frontier entries.
5. Candidate failure feedback is contextual and distinguishes candidate reverts from infrastructure/codegen failures.
6. QUBO operates on property-directed short horizons rather than a global unconstrained six-action universe.
7. One search evaluation corresponds to one concrete candidate.
8. Search-time execution avoids recompiling a new Solidity exploit for every ordinary candidate.
9. A search-time violation is minimized and then independently re-proven by the organizer Harness before exit `0`.
10. Exact submission Docker runs offline with locked/pinned toolchain semantics.
11. Sound control targets continue to produce no false `PROVEN` results.
12. Generalization benchmarks demonstrate improvement over the current v2 baseline without using target labels in production logic.

## 36. Non-goals

v2.5 does not attempt to provide:

- a proof that no exploit exists when search is exhausted;
- complete symbolic EVM execution;
- all Solidity ABI types in the first implementation;
- quantum advantage claims;
- mandatory quantum hardware;
- public-chain transaction broadcasting;
- LLM-dependent runtime search;
- vulnerability taxonomy classification as a search prerequisite.

## 37. Architectural summary

The current v2 proved that macro-free compiler-backed action discovery and generic exploit lowering are viable, but it still optimizes mostly over static action semantics. v2.5 inserts the missing layer between analysis and search: a property/resource model, runtime contract identities, state-dependent feasibility, contextual parameter completion, and an explicit frontier of reachable states.

QUBO remains important, but its responsibility becomes precise: rank short local action-ordering problems that have already been narrowed by property relevance and current state. It should not be asked to compensate for missing semantic slicing by optimizing an unnecessarily large global action universe.

The final system is therefore best described as a **Property-Directed Counterexample-Guided Portfolio Exploit Synthesizer** whose optimization backends propose candidates, whose runtime continuously refines the reachable-state model, and whose only authoritative success condition is a fresh organizer-Harness invariant violation.
