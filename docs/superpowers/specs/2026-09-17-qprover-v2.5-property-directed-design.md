# QProver v2.5 — Property-Directed Counterexample-Guided Portfolio Exploit Synthesizer

Date: 2026-09-17
Status: Design specification
Branch: `feat/qprover-v2.5-property-directed`

## 1. Purpose

QProver v2.5 redesigns the TRUST404 Track 04 path around one principle:

> Start from the supplied property, search for executable state transitions that make that property false, and use concrete EVM execution as the source of truth.

The system remains an exploit prover rather than a vulnerability classifier. It must not decide success from static analysis, QUBO score, source patterns, or a vulnerability label. A result is successful only when a generated standalone `Exploit.sol` violates an organizer-supplied invariant under the organizer Harness.

v2.5 replaces the remaining global static-sequence bias in v2 with a property-directed, state-aware counterexample search while preserving the strongest existing QProver components: compiler-backed analysis, typed dependency graph, generic search infrastructure, bounded SMT support, local execution, minimization, replay, and deterministic evidence.

## 2. Hard design constraints

### 2.1 No vulnerability-specific macros

Production search must not contain preconstructed attack families such as:

- reentrancy macro;
- oracle-manipulation macro;
- access-control macro;
- unchecked-accounting macro;
- target-specific exploit templates;
- public-target names, hashes, expected labels, or known witnesses.

A vulnerability class may be assigned after a witness is found for human explanation, but it must not be a planner input.

### 2.2 Execution is the referee

Static analysis, graph slicing, feasibility probes, best-first search, QUBO, coverage mutation, SMT, and runtime observations are prioritization or completion mechanisms only.

The final success condition is:

```text
organizer Harness
    -> Exploit.run(target)
    -> Invariants.checkAll(target)
    -> at least one supplied predicate returns false
```

### 2.3 Determinism

Given identical source bytes, manifest, toolchain, seed, and budget, the system must preserve deterministic ordering and deterministic output artifacts.

### 2.4 Official boundary remains unchanged

The external Track 04 interface remains:

```text
--contract
--invariants
--manifest
--out
--timeout
--seed
--max-attempts
```

Outputs remain:

- `Exploit.sol`
- `attempts.log`

Exit codes remain:

- `0`: organizer Harness confirmed an invariant violation;
- `1`: no confirmed witness within budget;
- `2`: invalid input or infrastructure/internal failure.

## 3. Current v2 assets to preserve

v2.5 must reuse rather than replace the following proven components where their semantics fit.

### 3.1 Compiler analysis

Keep `analysis.py` and extend it. Existing compiler-backed facts include:

- source-qualified contract/function identities;
- ABI selectors and mutability;
- storage reads/writes;
- internal/external/low-level calls;
- value flows;
- role guards;
- ordered external-call-before-write facts;
- transitive storage effects.

### 3.2 Program graph

Keep `graph.py` as the typed deterministic graph foundation. Extend it with resource-level relationships needed for cross-contract reasoning rather than replacing it with regex or source-text pattern matching.

### 3.3 Generic search core

Keep `SearchProblem`, `SearchController`, QUBO/BQM, risk/best-first, coverage-guided, random, and exact backends. v2.5 changes what problem is supplied to them and how feedback is represented.

### 3.4 Parameter and SMT infrastructure

Reuse the bounded Z3 machinery in `parameters.py` for solvable source-level integer constraints.

### 3.5 Execution and proof infrastructure

Reuse the concepts and components from:

- `evm.py`;
- `evaluator.py`;
- `minimizer.py`;
- `replay.py`;
- `certificate.py` where useful for development evidence.

The official Track 04 submission still outputs only the organizer-required artifacts.

## 4. Problems in v2 that v2.5 must solve

### 4.1 Invariant-blind ranking

The v2 Track 04 path currently builds utility primarily from generic function facts such as storage writes, storage reads, calls, and value flow. `Invariants.sol` does not materially direct action ranking.

This permits semantically unrelated public functions to dominate QUBO sequences.

### 4.2 Static path identity duplicates runtime contract instances

Getter paths such as:

```text
borrowToken()
pool()/bor()
```

may resolve to the same runtime address but are currently modeled as separate action targets.

### 4.3 Public ABI is not equivalent to attacker feasibility

A public/external function may be guarded, require prior state, require approval, or otherwise deterministically revert from the current state. Static inclusion alone creates large amounts of useless search mass.

### 4.4 Parameter generation is insufficiently contextual

Arguments are generated largely from per-type domains and runtime scalar references. The completer does not yet sufficiently bind an argument to surrounding actions, for example the spender of an approval to the next consumer contract.

### 4.5 Candidate-level Forge compilation is too expensive for search

Each attempted Track 04 candidate currently becomes Solidity and is recompiled/redeployed under Foundry. This is appropriate as a final proof boundary but too expensive and too information-poor for the inner search loop.

### 4.6 Feedback is compressed too aggressively

`revert_step=N` is useful but insufficient. A successful prefix is currently reduced mostly to an action penalty signal instead of becoming a retained search state.

### 4.7 QUBO receives too large and too weakly sliced a problem

A global six-step problem over all reachable actions encourages long, high-static-utility traces and increases BQM cost. QUBO should solve a smaller local ordering problem.

## 6. Compiler frontend

### 6.1 Compile complete trusted source closure

The frontend must compile the organizer target using the exact manifest compiler/EVM configuration and collect compiler evidence for:

- target source;
- imported source closure;
- setup code when present;
- invariant contract.

The original organizer files remain unchanged.

### 6.2 Invariant analysis

`Invariants.sol` must be compiled and represented as compiler-backed facts instead of being treated only as an opaque final checker.

For each manifest predicate, extract whatever can be established conservatively:

- target/native balance reads;
- target getter calls;
- external getter calls reachable from the target argument;
- constants used in comparisons;
- boolean/comparison structure;
- data dependencies of the returned boolean.

Unsupported expressions are allowed. Unsupported analysis reduces prioritization quality only and must never create a success verdict.

## 7. Property model

Introduce a `PropertySlice` abstraction.

```text
PropertySlice
- predicate_name
- source provenance
- observed resources
- relevant target/external getters
- relevant storage/resource ids
- relevant functions/actions
- optional comparison direction
- optional healthy boundary information
- analysis confidence/provenance
```

### 7.1 Backward slicing

For each property, walk backward from the property observations through resource reads and the program/resource graph to functions capable of affecting those resources.

The output is a relevance prior, not a proof of exploitability.

### 7.2 Directional information

When statically recoverable, preserve directions such as:

```text
balance(target) >= C   -> harmful direction is decreasing balance
value <= limit         -> harmful direction is increasing value or decreasing limit
owner == initial_owner -> harmful direction is changing owner
```

Do not infer a direction where compiler evidence is insufficient.

## 8. Resource graph

Storage alone is too narrow for cross-contract exploit reasoning. Extend the analysis graph with generic resources.

```text
ResourceKind
- STORAGE
- NATIVE_BALANCE
- EXTERNAL_VIEW
- TOKEN_BALANCE_LIKE
- ALLOWANCE_LIKE
- RETURN_VALUE
```

The names `TOKEN_BALANCE_LIKE` and `ALLOWANCE_LIKE` describe generic observed resource shapes; they must not encode a particular exploit class.

Actions may:

- read a resource;
- write/change a resource;
- transfer a resource;
- derive one resource from another;
- use one resource as an argument source.

The graph must support cross-contract chains where an action changes an external resource later observed through another contract.

## 9. Runtime contract-instance model

Introduce `ContractInstance`.

```text
ContractInstance
- runtime address
- code hash
- matched compiler artifact, if known
- ABI
- discovery paths
- provenance
```

### 9.1 Runtime alias deduplication

If multiple discovery paths resolve to the same address, merge them into one instance.

### 9.2 Discovery sources

Bounded deterministic discovery may use:

- public getters returning contract/interface types;
- public getters returning addresses when runtime code exists;
- known constructor/setup-created instances present in the compiler closure;
- runtime addresses observed from calls where soundly attributable.

Discovery must be capped and cycle-safe.

### 9.3 Code identity

Where possible, compare runtime bytecode/code hash against compiler artifacts to recover ABI/type identity. Unknown-code instances may be retained for low-level interaction only if the official environment permits it and the action representation remains deterministic.

## 10. State-aware action model

Replace the purely static action universe with actions plus runtime feasibility state.

```text
StateAwareAction
- logical action id
- ContractInstance target
- ABI signature
- parameter types
- payable flag
- static reads/writes/resources
- guards/modifiers
- property relevance
- current feasibility state
- provenance
```

### 10.1 Feasibility states

```text
FEASIBLE
REVERTS_NOW
UNKNOWN
```

A guarded action must not be permanently deleted merely because it is currently infeasible; prior actions may change the guard state.

### 10.2 Feasibility probing

Use cheap deterministic execution/dry-run probes on representative values to reduce obviously unusable actions from the current frontier.

Probing is a ranking signal. Failure to probe does not prove impossibility.

## 11. Search state and frontier

The central v2.5 search unit is a state, not a complete static sequence.

```text
SearchState
- relevant state fingerprint
- trace to reach it
- property observations
- resource observations
- feasible/known-infeasible actions
- trace features
- last outcome
- depth/cost
```

### 11.1 State fingerprint

The fingerprint should use property-relevant observations and selected resource observations, not a full copy of all EVM storage.

### 11.2 Dominance

If two traces reach the same relevant state, retain the shorter/cheaper trace unless the longer trace contains distinct callback/runtime capability required by future actions.

### 11.3 Successful-prefix retention

For a candidate:

```text
A -> B -> C -> D -> E(revert)
```

retain the state after `D` as a frontier state. Do not reduce this evidence only to an action-level revert penalty.

## 12. Planner portfolio

v2.5 uses multiple label-neutral planners sharing one frontier.

### 12.1 Deterministic best-first / graph planner

Prioritize short paths using:

- property relevance;
- resource/data dependency;
- current feasibility;
- novelty;
- trace length;
- execution feedback.

### 12.2 Rolling-horizon QUBO

QUBO remains a core planner, but its scope changes.

Instead of solving one global six-step problem over every reachable action, construct a local problem from the current state and property slice.

Recommended horizon:

```text
2 to 4 actions
```

The action set should be property-sliced and feasibility-filtered before BQM construction.

### 12.3 Coverage-guided mutation

Use state fingerprints and trace features to mutate useful prefixes, especially when static dependency ranking misses an unexpected execution path.

### 12.4 Portfolio scheduling

A deterministic scheduler allocates proposals among planners. No planner receives extra proof authority; all concrete candidates go through the same execution engine.

## 13. Iterative deepening

Prefer iterative depth over a large global STOP-encoded horizon.

```text
depth 1
depth 2
depth 3
...
```

or bounded rolling horizons from frontier states.

Benefits:

- naturally prioritizes short exploits;
- reduces BQM variables and couplers;
- reduces STOP encoding pressure;
- avoids tuning `length_weight` as the primary short-trace mechanism.

## 14. QUBO performance requirements

### 14.1 Sparse flip-delta evaluation

The current simulated annealing implementation must not scan every quadratic coupler for every bit flip.

Precompute per-variable adjacency/local-field structures so a flip can be evaluated in time proportional to the variable degree.

### 14.2 Sparse transition construction

Build quadratic transition terms from existing sparse transition edges rather than iterating all action pairs where avoidable.

### 14.3 Evidence

Record for each BQM:

- logical bit count;
- coupler count;
- reads/sweeps;
- solver wall time;
- action set size;
- horizon;
- property slice identity;
- state fingerprint identity.

## 15. Planner/completer separation

The planner proposes an abstract action skeleton. Parameter completion is a separate component.

```text
SkeletonPlanner
    -> ParameterCompleter
    -> ConcreteCandidate
    -> RuntimeEvaluator
```

One evaluation corresponds to one concrete candidate. Do not hide multiple concrete executions behind one planner observation.

This ensures feedback can be attributed separately to:

- bad action ordering;
- bad parameter choice;
- runtime feasibility.

## 16. Typed parameter expression IR

Represent dynamic values as expressions instead of opaque marker strings.

```text
ValueExpr
- Const(value)
- SelfAddress
- TargetAddress
- ContractAddress(instance_id)
- ReadUint(instance_id, signature, args)
- PreviousReturn(step, index)
- Scale(expr, numerator, denominator)
- Add/Sub/Min/Max where supported
```

Rendering to Solidity happens only at lowering time.

## 17. Contextual parameter completion

Candidate values come from:

- ABI boundaries;
- manifest values;
- source constants;
- current native/token-like balances;
- property/resource observations;
- getter values;
- previous return values;
- deterministic arithmetic transforms;
- SMT models from extracted guards.

### 17.1 Inter-action context

Parameter ranking may use generic relationships from neighboring actions.

Example:

```text
approve(spender, amount) -> call ContractInstance X
```

may rank `X` as a spender candidate because it is the next consumer target. This is a data/control relationship, not an approval-specific exploit macro.

### 17.2 Parameter feedback

A revert caused by one concrete value penalizes or constrains that value/context, not necessarily the action skeleton itself.

## 18. Bounded SMT completion

Reuse QProver's existing Z3 implementation for constraints that can be soundly extracted from source-level guards.

Examples of useful bounded constraints include integer comparisons/arithmetic from `require`/`assert` expressions involving action parameters, constants, and selected observed values.

Do not attempt full symbolic EVM execution in v2.5.

## 19. Generic SearchAttacker runtime

Introduce a reusable attacker contract for the inner search loop.

Required capabilities:

- execute a bounded list of generic calls;
- evaluate dynamic `ValueExpr` reads;
- retain temporary return values;
- receive native value;
- dispatch bounded callback programs;
- expose deterministic execution markers.

The runtime must preserve official semantic essentials, especially that target contracts see the attacker contract as `msg.sender` where the final `Exploit.sol` would do so.

## 20. Generic callback program

Replace the current same-call callback model with a generic bounded callback program.

```text
CallbackProgram
- trigger step
- allowed caller/selector conditions where known
- bounded instruction sequence
- maximum depth
```

Possible callback body:

```text
CALL B
CALL C
READ X
CALL D
```

The representation must not contain a vulnerability-class field.

## 21. Fast runtime evaluator

The inner loop should execute on a persistent local Anvil or equivalent deterministic local EVM.

Workflow:

```text
compile once
-> deploy baseline once
-> deploy SearchAttacker once
-> snapshot
-> execute concrete candidate
-> collect trace/state/property evidence
-> revert snapshot
-> repeat
```

### 21.1 Required feedback

For every concrete candidate collect, when available:

- PASS / REVERT / VIOLATION / INCONCLUSIVE / INFRA_ERROR;
- exact failing step;
- raw/normalized revert data;
- trace features;
- relevant resource observations before/after;
- property observation before/after;
- state fingerprint;
- successful prefix length.

## 22. Error taxonomy

Do not merge candidate reverts with tooling failures.

Use categories equivalent to:

```text
CANDIDATE_REVERT
CANDIDATE_PASS
CANDIDATE_VIOLATION
CODEGEN_COMPILE_ERROR
SETUP_ERROR
HARNESS_ERROR
RPC_ERROR
TIMEOUT
```

Only candidate-level execution outcomes may be used as exploit-search feedback. Infrastructure/code-generation failures must be handled separately.

## 23. Revert-data preservation

The generic attacker and final generated exploit should preserve target revert bytes where practical.

Development feedback should distinguish:

- `Error(string)`;
- `Panic(uint256)`;
- custom error selector/data;
- empty revert;
- infrastructure failure.

The official deterministic `attempts.log` may normalize this to stable compact fields.

## 24. Counterexample-guided repair

Failed concrete candidates update both planning and completion.

Examples:

- failing first action -> lower current-state feasibility;
- successful prefix -> create/retain frontier state;
- failing parameter with same skeleton -> mutate/solve parameters first;
- successful resource-changing action -> increase relevance of dependent consumers;
- newly observed contract address -> update instance graph within caps.

Feedback must be state/context-sensitive rather than a global statement that an action is bad.

## 25. Property progress

Where a property can be reduced to a directional numeric observation, use distance-to-boundary as a prioritization signal.

Examples:

```text
balance >= C  -> smaller balance is closer to violation
x <= y        -> larger x-y is closer to violation
```

If such a metric cannot be established conservatively, use only state novelty/dependency relevance.

Progress score is never a proof.

## 26. Final exploit IR and lowering

The final witness uses a generic exploit instruction IR.

```text
CALL
READ
STORE_TEMP
CALLBACK_CONFIGURE
CALLBACK_CLEAR
```

No vulnerability-specific renderer is allowed.

The final lowering produces:

```solidity
contract Exploit {
    function run(address target) external payable {
        // deterministic generic witness
    }
}
```

## 27. Search proof versus final proof

Separate the two roles explicitly.

### 27.1 Search evaluator

Fast, state-rich, persistent execution used only to discover a witness.

### 27.2 Organizer proof

After a witness is found:

```text
minimize
-> render standalone Exploit.sol
-> fresh organizer Harness verification
-> if verified, output exit 0
```

The organizer Harness remains the authoritative final result.

## 28. Minimization

Connect the existing execution-backed minimizer to Track 04.

Minimum required operators:

- contiguous chunk deletion;
- one-step deletion;
- parameter simplification;
- call-value simplification;
- callback-program simplification.

The minimized witness must be freshly reverified under the official Harness. If minimization loses the violation, retain the last verified witness.

## 29. Attempts log

`attempts.log` remains deterministic and compact but should distinguish concrete execution information.

Suggested fields:

```text
attempt
planner
state
result
violated
candidate
skeleton
revert_step
revert_kind
note
```

Avoid nondeterministic wall timestamps in the official log.

## 30. Budget model

The top-level timeout is a true wall-clock budget covering:

- compilation/analysis;
- runtime preparation;
- planning;
- concrete execution;
- final Harness proof.

No new verification may begin after the deadline.

The attempt budget counts organizer-level concrete attempts in a clearly defined way. Internal cheap feasibility probes must have their own bounded deterministic cap and must not silently consume unbounded time.

## 31. Reproducibility and toolchain

Submission validation must use the exact submission toolchain.

Required submission CI path:

```text
build exact linux/amd64 Docker image
-> verify pinned solc
-> verify pinned Foundry
-> verify pinned Python/dependency environment
-> run with --network=none
-> focused Track04 tests
-> public target regression
-> determinism regression
```

The Python environment inside Docker must be derived from the committed lockfile or another equally strict pinned dependency mechanism rather than resolving unconstrained dependencies with plain `pip install .`.

Host/unit CI may additionally test other supported Python versions, but a green host CI must not substitute for submission-image CI.

## 32. Benchmark and generalization strategy

Do not tune solely against the six public organizer targets.

Create hidden-like metamorphic benchmark families using transformations such as:

- function and variable renaming;
- equivalent helper extraction/inlining;
- reordered declarations;
- different wrapper/getter topology;
- extra irrelevant public functions;
- alternate guard syntax;
- address-return getters instead of contract-typed getters;
- equivalent callback structure;
- same semantic vulnerability with different constants/scales;
- sound twins.

Production search must not access benchmark labels or witnesses.

## 33. Ablations required

Measure at least:

```text
best-first only
QUBO only
coverage only
best-first + QUBO
portfolio without PropertySlice
full portfolio with PropertySlice
full system without state frontier
full system without SMT completion
```

Report:

- confirmed-positive rate;
- false-confirmed rate on sound controls;
- median candidates to proof;
- wall time;
- planner time versus EVM time;
- BQM bits/couplers;
- candidate length;
- codegen/final-proof failure rate.

No quantum advantage claim is made.

## 34. Compatibility and non-goals

v2.5 does not require:

- public-chain broadcast;
- wallets/private keys;
- an LLM at runtime;
- full formal verification;
- full symbolic EVM;
- support for every Solidity ABI shape in the first implementation;
- proof that search exhaustion implies safety;
- a quantum-hardware backend.

Unsupported features must fail closed or degrade search coverage without producing false PROVEN results.

## 35. Proposed module boundaries

The implementation should move responsibilities out of the growing Track04 monolith into explicit components.

Suggested modules:

```text
trust404.py
    official manifest/types/public adapter surface

trust404_analysis.py
    compiler workspace and target/invariant compilation

trust404_property.py
    PropertySlice construction

trust404_instances.py
    runtime ContractInstance discovery/deduplication

trust404_resources.py
    resource graph and action effects

trust404_actions.py
    state-aware attacker action construction

trust404_values.py
    ValueExpr and contextual parameter completion

trust404_runtime.py
    SearchAttacker + persistent EVM evaluator

trust404_frontier.py
    SearchState, dominance, successful-prefix frontier

trust404_planner.py
    portfolio scheduler / rolling planning adapter

trust404_codegen.py
    generic final Exploit IR lowering

trust404_runner.py
    budget orchestration and official output boundary

trust404_harness.py
    authoritative organizer Harness verifier
```

Exact file names may change during planning, but each responsibility must remain independently testable.

## 36. Migration strategy

Do not replace the whole system in one commit.

Migration must preserve a working official adapter after each major phase.

Recommended architectural phases:

### Phase A — Property-directed static model

- compile/analyze invariant contract;
- build `PropertySlice`;
- add resource graph;
- runtime contract-instance alias dedupe;
- slice action set by property relevance;
- retain current official verifier.

### Phase B — Search quality and QUBO efficiency

- sparse annealing flip delta;
- sparse BQM transitions;
- iterative/rolling horizon;
- best-first + QUBO portfolio;
- explicit planner/completer separation.

### Phase C — Stateful runtime

- reusable SearchAttacker;
- persistent local EVM baseline;
- snapshot/revert candidate execution;
- state fingerprints;
- successful-prefix frontier;
- richer revert/resource feedback.

### Phase D — Parameter reasoning

- typed `ValueExpr`;
- contextual address/value binding;
- guard constraint extraction;
- bounded Z3 completion;
- previous-return/resource-derived values.

### Phase E — Generic callback and final proof pipeline

- bounded callback programs;
- Track04 minimization;
- final generic Exploit lowering;
- fresh organizer Harness proof.

### Phase F — Reproducibility and generalization gates

- exact Docker CI;
- lockfile-enforced environment;
- public regression;
- metamorphic hidden-like benchmark;
- deterministic repeated runs;
- ablation report.

## 37. Acceptance criteria

### Architecture

- no vulnerability-specific macro or target-specific production branch;
- property analysis materially affects the search problem;
- reachable runtime aliases are canonicalized;
- one concrete candidate maps to one evaluator result;
- successful prefixes become reusable frontier states;
- final proof remains organizer Harness based.

### Performance

- QUBO is applied only to bounded property-sliced local action sets;
- annealing flip delta uses sparse adjacency rather than full-coupler scans;
- candidate search does not require Solidity recompilation per attempt once the fast runtime phase is enabled.

### Soundness

- no invariant violation -> never exit 0;
- infrastructure/codegen failures are not learned as candidate semantic reverts;
- safe controls do not produce false PROVEN results;
- timeout is enforced across the entire run.

### Generalization

- public target names/known witnesses absent from production;
- macro-free public positives are measured but are not the only benchmark;
- metamorphic semantic variants are included before considering v2.5 complete.

### Reproducibility

- exact submission Docker toolchain is CI-tested;
- offline run succeeds;
- identical seed/input/toolchain produces deterministic official artifacts.

## 38. Design conclusion

QProver v2.5 should not become a larger library of attack heuristics. Its core abstraction is:

```text
property
    -> relevant resources/state
    -> currently feasible state transitions
    -> short planner proposal
    -> contextual parameter completion
    -> concrete execution
    -> retained state/feedback
    -> counterexample
```

QUBO remains valuable as one optimizer inside this architecture, especially for short action-ordering subproblems. It is not responsible for discovering the entire exploit in one global optimization problem and it is never a truth oracle.

The official organizer Harness remains the final authority. The fast stateful runtime exists to make search cheaper and more informative, not to weaken proof semantics.
